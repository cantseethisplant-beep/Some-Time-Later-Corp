# Startup, durable keys, recovery and selected pilot targets

Normative proposed policy. No migration, encryption, backup or restore exercise has run for the future app. The pinned integration packet shows Data Protection keys persisted in Redis under `DataProtection-Keys`; Redis cannot simply be treated as expendable cache. The same packet's migration helper logs an exception without rethrowing. v3 requires explicit changes and checks rather than calling those source paths safe.

## Selected persistence profile

Use private PostgreSQL for core+module data. Keep base Redis cache, but **move Data Protection key persistence to a dedicated durable filesystem key directory** in the maintained bridge/startup patch, preserving application name `WHMapper` and purpose isolation. Protect keys at rest with a deployment X.509 certificate; its private key is mounted read-only from operator secret storage, never baked into an image or Git. POSIX owner permissions 0700 directory/0600 files, encrypted volume/backup, restricted runtime identity. Existing Redis key migration is an explicit maintenance action: export the actual ring, import to the new provider with certificate protection and demonstrate protected-payload continuity before discarding old state. For a fresh fixture install, generate a new ring/certificate. If provider interoperability cannot be demonstrated on an existing install, block migration rather than silently destroy the old keys. No arbitrary custom key format is defined here.

Keep the previous key ring and decrypting certificate until all retained data/backups needing them expire; key rotation must not invalidate still-required backup material. Recovering a ring without its decrypting key is not a passing restore. Data Protection is not assumed to be the token store or a full-disk encryption system. Baseline inventory must list actual token/cache/protected-storage consumers and any additional Redis state; unidentified durable state blocks qualification.

Microsoft documents key-provider configuration and the need to configure at-rest key protection when choosing explicit persistence: [key storage providers](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/implementation/key-storage-providers?view=aspnetcore-10.0). This source supports the mechanism, not a completed app migration or tested recovery claim.

## Migration ownership and readiness

One operator deployment job owns migration. Remove automatic production `MigrateAsync` application-start writes from the maintained base entry point. Generate reviewed SQL/bundles from locked inputs, retain hashes, take a recoverable backup, stop app writes, acquire a PostgreSQL session advisory lock reserved for this deployment, then apply core and module migrations in the manifest's recorded order. Separate core/tools/hosting history tables, each compared to exact expected migration IDs. Release the lock only after verification. Runtime role has no schema-change rights; migration credentials do not go to the normal app process. A bundle may contain transactions as generated; do not assume all migrations across contexts are one atomic operation.

Normal startup is read-only schema verification. Missing/extra/incompatible **base** history, a prior incomplete base migration marker, inaccessible keys/DB or an unqualified shared dependency -> readiness false, no product ingress; expose only private redacted health, then exit nonzero after a 60-second bounded startup window. A module-only schema/version mismatch disables that module's routes/events/jobs and sets its readiness false while a qualified compatible base can remain available; it cannot satisfy a release profile that requires the failed module. Incomplete module migration also quarantines its schema until explicit deployment recovery. No catch-and-log continuation serving incompatible routes. Private liveness says process alive; base readiness and each module readiness are separate, and selected-release readiness is their required conjunction. Never infer app readiness from a PID, initial page or successful tunnel handshake.

Migration failure keeps maintenance mode and marks deployment failed. Restore the last qualified consistent generation or perform a reviewed forward recovery; never automatically retry destructive Down migrations. Test partial failure and competing migration job against synthetic data. The second job must fail lock acquisition without effects. EF's own version-specific locks do not replace the deployment ownership and evidence policy. [EF applying migrations](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying) distinguishes deployment and runtime privileges and calls for migration inspection/testing.

## Backup, deletion journal and failure policy

Selected small-pilot policy: one encrypted full generation every 24 hours, keep seven daily generations for no longer than seven days. Each includes a transactionally consistent core+module PostgreSQL dump, required key ring/certificate recovery material, compatible source/image/migration manifest, encrypted configuration excluding disposable sessions, and a checksum/creation/custody receipt. Redis is disposable only after the baseline inventory proves remaining content is cache; otherwise include its durable state in the same generation. During generation hold maintenance/write gates until DB/key/config consistency is recorded. Never publish these archives or real inventories to GitHub.

Selected deployment role: operator-controlled encrypted backup storage independent of the production origin, privately configured and qualified before live use. The always-on server AI/build host may fill this role only if it is a separate failure domain from the selected origin and has explicit custody/space/availability approval; it is not assumed qualified. The laptop can hold an optional offline extra copy, with no required availability or runtime role. A second volume on the Oracle VM is not off-host. Before live use the operator must supply actual destination, encryption recovery identity and space/refresh responsibility and demonstrate retrieval with the VM unavailable. Missing/offline destination or no successful generation in the last 24 hours sets backup-degraded, disables new private-data writes and alerts the operator; it never purchases storage automatically.

To prevent resurrected deleted notes/revoked grants from an older daily backup, selected live profile also requires an off-host **metadata-only recovery journal** receiver under operator custody. Configuration supplies one fixed HTTPS URL and pinned receiver identity outside Git; no caller-provided URL. Mutual TLS authenticates sender/receiver; each entry has UUID, ordered sequence, previous-entry hash, command hash, map/character/record IDs, deny/delete kind and UTC, no note text/secrets. Receiver fsyncs before returning an authenticated receipt for the entry hash/sequence. Same UUID/same hash returns same receipt, changed hash rejects. It is append-only to the app identity, retained 14 days. The receiver runs on a qualified always-on recovery host independent of the production origin. It must continue when the laptop is shut down. The build server may fill that role only after role/custody/failure-domain qualification; a directory or second container on the origin does not qualify.

For delete/revoke/owner-recovery operations: follow 03 initial admission, including existing-key lookup, deadline, revision and author/target validation BEFORE any journal append; acquire its ordered in-process gates and persist a prepared metadata journal record in a short transaction, close it, then append conservative deny/delete intent off-host **before opening the effect transaction or sending success**. No network wait occurs inside a database transaction. Persist the authenticated receipt, revalidate authorization/revision and commit the effect plus intent/audit/receipt under the gates. If the effect transaction rolls back, replay may conservatively suppress a note/grant until operator review; it must never grant access or recreate text. Journal timeout -> 503 STORAGE_UNAVAILABLE, no success, reconcile same journal UUID and intent on retry. A receipt with unknown outcome is never blindly replaced by a new UUID. If journal receiver is unavailable, these actions are not acknowledged, affected scope is immediately suspended in the local epoch/gate, and the UI says pending recovery safety, not “deleted/revoked.” Suspension/reconcile-required is persisted in its own bounded transaction before releasing gates. If even that write fails, stop product ingress and exit; process restart must see unresolved prepared journal entries and retain maintenance/suspension. New contributions in suspended scope are denied. Existing read access in that scope is also denied until journal/DB reconciliation; other scopes remain governed normally. An authorized identical retry of a previously completed security command reads its saved receipt/result rather than requiring a new remote append; revoked access still cannot retrieve private result bodies.

This profile requires independent durable recovery availability; it does not tie any live operation to the laptop or imply a free service is already available. The future operator must choose to meet this profile or approve a separately specified durable receiver; no hidden cloud product fills the gap. A receiver lag/certificate/space fault is a deployment blocker. This is not an unbounded distributed effect engine; only append-only deny/delete metadata is accepted.

Journal wire contract: fixed `POST /v1/journal` on the configured receiver, mTLS only, no redirects, 5-second total timeout, at most one automatic attempt per handler. Request JSON has deploymentId UUID, entryId UUID, sequence positive safe int64, previousHash lowercase 64-hex (genesis zeros), kind enum note.delete/access.revoke/consent.disable/owner.recover/scope.deny, scopeKind enum map/instance, scopeId positive int32, targetId UUID-or-positive-int32-or-null, commandHash lowercase 64-hex, recordedAt UTC milliseconds. It contains no arbitrary nested payload/text. Body <=4096 bytes; duplicate/unknown fields rejected. Entry hash is SHA-256 of compact ordered JSON fields in the order just listed, Unicode unescaped. Receiver serializes by deploymentId and accepts sequence=prior+1 with matching previousHash; gap or different hash for known entryId is 409. Same entryId/same hash returns existing receipt even when sequence has advanced. Receipt fields are deploymentId, entryId, sequence, entryHash, receivedAt, all bound to the authenticated receiver; 201 new/200 existing. Fail before fsync returns no success. Sender verifies all identity/hash fields and persists receipt; timeout is reconciled with an identical POST, never a new entry. Server auth/size/schema rejection is terminal until diagnosed. Receiver is an operator utility to be implemented/qualified during operating work, not an existing service or a third user-facing product module. Its source/image/certificate identities belong to the release manifest.

Restore/export contract: the append-only application identity cannot export/read the journal. A separate recovery-operator identity runs receiver-side `journal-export --deployment-id <UUID> --after-sequence <backup-checkpoint> --through-sequence <head>`, producing exact retained entries, initial checkpoint and terminal head hashes. The backup records its acknowledged journal sequence/hash in the encrypted manifest. Restore verifies continuity from that checkpoint to the freshly exported authenticated head; no skipped sequence or fabricated genesis. Keep a checkpoint anchor and every entry needed by the oldest retained backup; retention may remove earlier entries only after all referencing backups expire. Missing tail/anchor/export identity blocks serving restored data. Receiver has a durable head per deployment even when old entries are pruned. Its reset or loss is an incident requiring a new reviewed deployment epoch, not sequence reuse.

## Isolated restore procedure and targets

Selected qualification targets (requirements, not measured promises): ordinary-data RPO <=24 hours, acknowledged deny/delete decision RPO zero through the off-host journal, operator-attended RTO <=4 hours from starting a restore with recoverable material available. No promise of unattended 24/7 recovery or Oracle replacement capacity.

1. Restore on an isolated target with outbound CCP/provider calls and public tunnel disabled. Verify generation manifest/digests, source/image/schema compatibility, decrypting keys and journal chain/receipts. Missing chain after backup -> Tools remains disabled; never serve restored note text until resolved.
2. Restore core/module DB and required secrets/ring. Apply journal entries newer than the generation, conservatively tombstone/revoke by identity even if a prepared intent never committed. Verify IDs, revisions, owner/map links, timestamps and known fixture content. Expired grants/consent stay expired.
3. Increment global restore epoch; invalidate **all** restored module grants/consents, cursors and sessions. Clear restored login/refresh/session caches and require fresh base authentication under an operator-reviewed base credential shutdown plan. Do not restore an old accepted browser session merely because a recovered cookie decrypts. Base ACL review and module re-pairing/regrant are explicit operator actions. Preserve old ring only for required data recovery; identify which protected values remain readable.
4. Run negative cross-map/access, deletion-resurrection, login, callback, migration and notes workflow checks; record timings and evidence. Generate a new backup and validate current off-host journal receipt before reopening. Only then enable a separately approved tunnel/domain. If anything fails, stay isolated/maintenance.

Evidence includes generation identity and redacted hashes, measured timings, preserved integer core/UUID module references, deleted-text absence, denied revoked access and fresh-login success. A dump file's existence is not a restore pass. Scheduled expiry/retention targets and backup deletion are tested separately; generations exceeding seven days are removed by operator-controlled retention, not retained indefinitely by accident.
