# Module data and commit semantics

Normative P0. PostgreSQL is the selected storage, following the pinned mapper. One instance of the app process; multiple users/maps are allowed. Separate DbContext/migration history and schema `wh_tools`; no rewrite of upstream core keys. Select the exact SDK/packages and image digests in the authorised baseline build and freeze them; .NET target declarations are not dependency locks.

## Tables and invariants

All UUIDs generated server-side except requestId; use PostgreSQL uuid. Core/character IDs int32 positive. Times timestamptz UTC, output truncated to milliseconds. Revisions/sequence bigint positive; no floating JSON numbers. Clients must use safe int64 parsing; reject values beyond 9007199254740991 in JSON contract v1. Identifiers must never wrap/recycle. No raw credentials in these tables.

| Table | Keys / data / constraints |
|---|---|
| owner | instance_id PK, character_id, revision, epoch, paired_at; unique one owner/instance |
| map_state | map_id PK, resolved_instance_id, base_epoch, module_epoch, next_sequence; revisions >=1; mapped core reference verified |
| grant | (map_id,character_id) PK; view, annotate, expires_at nullable, revision; annotate implies view; both false -> no expiry |
| consent | (map_id,character_id) PK; enabled, expires_at nullable, revision; default absent false/rev0 |
| annotation | id PK UUID; map_id, instance_id, system_id, author_id, observed_at, recorded_at, updated_at, expires_at, revision, text nullable, deleted_at nullable, created_sequence; immutable map/system/author/observation/source fields; active text not null; tombstone text null |
| annotation_history | (annotation_id,revision) PK; prior text and content times; purge text versions after 30 days; delete purges all prior text immediately |

Use restrictive references from module tables to existing core map/system rows after confirming actual schema/table names in the baseline. P0 bridge intercepts base deletion/reparenting: exclusive gate, expire/tombstone affected notes and invalidate module grants/cursors/subscriptions in the same reviewed database transaction as the base action, or reject the base action with a clear “module data attached” conflict. **Selected initial policy: reject base deletion/reparenting with active module references**; manager deletes module notes and operator explicitly detaches inactive module history before retry. Never cascade-delete core data from a module. A core row disappearing outside supported app paths makes the module scope unavailable, produces a metadata audit and blocks delivery; direct operator SQL is outside ordinary runtime guarantees and requires maintenance/reconciliation.

P0 annotation writes touch module schema only. Source and uncertainty are fixed server values manual/reported, not stored as untrusted caller claims. No core observation ingestion or corroboration state is present. Future additions require new schema/API version and provenance tests. Text must meet contract validation before transaction. History is for an authorized administrator's recovery operations, not an undeclared historical read API.

## Mutation order and atomicity

1. Validate transport size/media/JSON shape, authentication, origin/antiforgery and actor rate limit. Resolve route map/system; collect sufficiently fresh membership evidence. Acquire per-character then per-map shared gates as in 01. Evaluate base permission and active module capability/consent; reject before looking up private idempotency/current bodies. Recheck evidence expiry and any invalidation epoch while holding gates.
2. Canonicalize validated payload with normalized LF text and exact UTC milliseconds; omit requestId only. SHA-256 input is UTF-8 compact JSON object with properties in order `operation`, `mapId`, `resourceId`, `body`. operation is TO-02/03/08/09/10; resourceId is null for create, annotation UUID for edit/delete, own character integer for consent, target character integer for grant. Body properties follow their order in the named schema's `properties`, excluding requestId; intentExpiresAt remains included. Integer formatting is plain decimal without exponent/fraction, null/boolean are JSON literals, Unicode unescaped except required JSON quotes/backslash/control escapes, no insignificant whitespace. Store that exact digest. No runtime dependency on unspecified serializer/dictionary ordering.
3. For security delete/revoke/recovery commands, perform the off-host journal preparation in 05 while holding the in-process gates, before opening the database write transaction. Open PostgreSQL transaction at SERIALIZABLE. Lock map_state row, then applicable grant, consent, annotation and intent rows in that order; increasing character/record IDs within a class. Lock/check relevant grant/consent and epoch rows before committing. Revalidate any pre-journal expected revision/authorization; a conservative journal entry does not force a stale command to commit. Unique intent key serializes identical concurrent commands; handle conflict by reading committed row after bounded retry. Unknown commit outcome must be resolved through the existing key, never a new key.
4. If matching committed intent exists, return prior result only after current access/capability/consent check; changed canonical hash/operation/resource -> 409 IDEMPOTENCY_CONFLICT. A revoked subject cannot use an old success to retrieve private text. If result expired -> 410 RESULT_EXPIRED. Otherwise validate initial intent deadline, expectedRevision and author/target rules. Serialization/deadlock retry at most twice after first attempt, same intent, bounded 25 then 75 ms delay; after three attempts return STORAGE_UNAVAILABLE and allow explicit same-intent retry. These retries never make external provider calls.
5. Write effect, history/audit, next per-map sequence, outbox and successful intent result in **one** transaction. Delete nulls text/history and stores a metadata tombstone, revision+1; repeat same delete intent returns its tombstone. Different delete intent on an already deleted record returns 404 with no new success effect. A semantic conflict/validation denial rolls back and is not persisted as a successful intent. Do not emit success/event before commit. Failed transaction leaves no partial effect or success key.
6. Commit; only then respond. Gate remains held until commit and response decision. Outbox dispatcher sends invalidation after commit using authorized recipients. A send failure never rolls back an acknowledged note; retry invalidation at most ten times with exponential delay capped at 60 seconds, then log metadata and rely on current-state revalidation. Delivery is at-least-once; duplicate eventId is ignored by the UI. Mark delivered means attempted delivery to currently authorized connections, not proof every browser saw it. Retain delivered outbox metadata 24 hours, failed metadata 7 days.

Delete and retention expiry also scrub affected text from prior intent result bodies and app caches in the same protected scope. An otherwise valid retry for a scrubbed/deleted/expired annotation returns 410 RESULT_EXPIRED rather than revealing the old body; the successful delete intent may still return its metadata tombstone. This privacy exception takes precedence over replaying an original create/edit response. The corresponding text history is also purged; metadata intent key/digest remains until ledger expiry. Every replay checks current record deletion/expiry before disclosing a stored body.

Concurrent content updates with the same revision: one commits, another returns 409 with authorized current record. They do not silently overwrite. Deletion/expiry/revoke races are resolved by gate/row/revision order. A stale saved grant cannot authorize after revoke acknowledgment. There is no claim to learn an external corporation change before its bounded source freshness allows it. There is no distributed transaction with core scan writes or HostingController in P0.

## Retention and revocation durability

Run metadata/text retention sweep hourly, max 1000 rows per transaction; ordinary reads immediately filter expires_at <= now even before sweep. A delete response is not sent until text removal committed. Append deletion tombstone and access/consent/owner revocations to the private recovery journal before reporting those security actions successful; see 05 for failure mode. Journal includes no note text and remains for 14 days. Backup restores apply journal entries newer than backup before live serving, preserving deny/delete decisions. Deleting an actor's contribution consent does not silently erase other actors' notes or erase audit; the displayed policy in 01 is authoritative.

## Module disabled or mismatched

When Tools is disabled: no Tools product routes, collection, dispatcher or hub; operator may inspect compatibility/readiness via private administration only. Data is retained under the recorded policy; purge requires explicit maintenance action. Module migrations never run implicitly on toggling a flag. App may run the qualified base with Tools off; it may not claim Tools ready with mismatched schema. Uninstall must export an encrypted operator archive or record an explicit reviewed discard; no live remote workloads/core maps deleted.
