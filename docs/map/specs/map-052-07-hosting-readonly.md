# Optional Hosting ledger — exact P0 boundary

Separate module ID hosting, planned version 0.1.0, disabled by default. It is not needed to run WHMapper/Tools on Oracle. This P0 slice is a metadata ledger, not a machine enrollment, health-monitoring or deployment system. No provider SDK, shell/remote command, arbitrary URL fetch, OCI/Cloudflare action, node agent, controller dispatch or workload assignment is installed/enabled. The current backend is externally managed and cannot be destroyed through this module.

## Roles and scope

Every operation requires verified current base character plus `IsEveMapperInstanceAccessAuthorized` for the route instance, with the freshness/failure policy of 01. Roles: hosting.viewer (read redacted offers/requests), hosting.requester (record requests), hosting.operator (record operator approval), hosting.owner (offer creation and ownership operations). Role membership is explicit character/instance, expires at most 30 days. Every product operation also requires hosting.viewer; role assignment does not implicitly add other roles. HO-02 create requires hosting.owner and derives new owner from session; subsequent offer changes/owner approvals additionally require actor=stored offer owner. HO-03 requires hosting.requester. HO-04 requires hosting.owner for the host-owner decision or hosting.operator for operator decision. HO-06 permits the stored requester, stored offer owner with owner role, or operator; subject must still have its applicable current role. Tools grants and map/corp admin are insufficient. Roles are paired/revoked offline by operator command after verified base instance-admin approval; revoke invalidates subscriptions/results. No public self-enrollment/self-claim or browser role escalation.

HTTP prefix `/api/modules/hosting/v1/instances/{instanceId}`. Same transport/authentication, antiforgery, origin/no-cache, envelope, validation, status/idempotency/retention policies as Tools. Role pairing records are separate. Instance epoch serializes grants/withdrawal/approvals. Metadata schema `hosting`, separate migration history. Each update increments revision; all bodies reject unknown properties. Max 16 KiB decompressed, string limits below in Unicode scalars. No instance/map/actor can be overridden in body.

## Entities, routes and exact fields

| ID | Method/suffix | Body beyond shared mutation envelope | Result |
|---|---|---|---|
| HO-01 | GET `/offers?limit=1..100&cursor=...` | No body; default 50, opaque ten-minute instance/actor/epoch/filter-bound cursor | items of Offer, nextCursor; owner private contact and secrets never present |
| HO-02 | POST `/offers` | label 1..100, description 0..2000, architecture enum arm64/x64/unknown, region 0..100, maxCpu integer 0..64, maxRamMiB integer 0..1048576, expiresAt now+60sec..30days | Offer UUID/rev1; creator is owner; values explicitly owner-declared, zero means not offered |
| HO-02 | PATCH `/offers/{id}` | expectedRevision, same full offer fields plus available boolean | Owner only; identity immutable; changing/withdrawing invalidates unapproved requests; no workload deletion |
| HO-03 | POST `/requests` | offerId UUID, operation enum request.record, purpose 1..1000, expectedOfferRevision >=1, expiresAt now+60sec..7days | Request UUID/rev1 pending-approval; no execution |
| HO-04 | POST `/requests/{id}/approvals` | expectedRevision >=1, role enum host-owner/operator, decision approve/reject, reason 0..1000, expiresAt now+60sec..24hours | Request revision+1 plus Approval; effective expiry min(request,offer,approval expiry) |
| HO-05 | execution | No registered route/dispatcher/worker | MODULE_OPERATION_UNAVAILABLE internally; HTTP unmatched 404 |
| HO-06 | POST `/requests/{id}/cancel` | expectedRevision >=1, reason 0..1000 | Request cancelled; requester, offer owner or operator; no remote cancellation/effect |
| HO-07 | lifecycle plan | No registered route in P0 | Use operator backup/runbook in 05; never mark restore passed from a request record |

GET `/offers/{id}` and `/requests/{id}` give authorized same-instance record or 404; GET `/requests` uses same pagination rules and only records actor requested/owns or operator can inspect. No broad cross-tenant query. P0 health is always `unknown`, healthSource=`none`, observedAt=null. Owner availability is `ownerDeclaredAvailable`, not an authenticated node heartbeat. Static capability claims are not measured capacity, free quota or scheduling authority.

Offer result: id, instanceId, ownerCharacterId, label, description, architecture, region, maxCpu, maxRamMiB, ownerDeclaredAvailable, expiresAt, revision, health=unknown, healthSource=none, observedAt=null, externalManaged=true. Create sets ownerDeclaredAvailable=true. Request: id, instanceId, offerId, requesterId, operation=request.record, purpose, boundOfferRevision, payloadHash, expiresAt, revision, state, approvals array. Approval: id, approvingCharacterId, role, decision, reason, payloadHash, expiresAt, recordedAt. All IDs typed as above, all times exact UTC milliseconds. Payload hash is server-generated canonical SHA-256 of immutable request fields plus bound offer revision; no browser-supplied trusted hash.

## Approval state machine and retention

Request state pending-approval → approved-record-only or rejected; pending/approved-record-only → cancelled/expired/invalidated. Two distinct people are required: current host owner and explicit hosting.operator, neither equal to requester and not equal to each other. A host owner who is also an operator can supply only one of the two approvals. First valid rejection makes rejected terminal. Two current approvals of exact payload and unchanged offer yield approved-record-only; **never executing or succeeded**. Editing offer revision or withdrawing it invalidates pending/approved requests. Expiry is enforced on every read/write even if a background sweep has not run. Cancellation/rejection/expiry cannot be revived; make a new explicit request. Every decision/result/event is bound to current scope and revision; duplicate key follows the original result subject to reauthorization. All writes, audit and invalidation outbox are a single Hosting transaction, with no external provider effects.

No offer/request promises a supported application catalogue, passive ISK, donor-host privacy, billing or remote credentials. The UI prominently states “Record only — no deployment or verified health.” A grant/role/approval revoke uses the durable deny journal policy before acknowledgment; no pending remote execution is queued while module/controller is absent. With module off there are no product routes/jobs/events. Keep metadata/audit 90 days after terminal state or offer expiry, then purge; no live workloads are ever deleted by ledger retention. Operator recovery/export is encrypted and private.

The later execution service requires its own typed transport, key issuance, enrollment, attestation limits, payload-bound dual approval, effect/idempotency/reconciliation, quota and fencing contract. None can be inferred from an approved-record-only ledger. Q23 proves this feature has no remote effects, not that hosting automation works.
